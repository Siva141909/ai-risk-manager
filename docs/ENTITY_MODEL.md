# Entity Model — Phase 1B/1C

**These entities are not real Razorpay identities.** Every entity below is
either (a) a real IEEE-CIS column used as-is, (b) a **derived proxy**
computed from real columns with an explicit, evidence-bounded confidence
level, or (c) a **fully synthetic overlay** with no real-data basis at
all. Code and downstream docs must always carry this distinction — see
`REAL` / `DERIVED PROXY` / `SYNTHETIC` tags throughout.

## 2. Terminology contract

- **REAL** — the exact value from the IEEE-CIS file, never altered.
- **DERIVED PROXY** — computed deterministically from real columns, but
  is an approximation of something IEEE-CIS does not actually label
  (customer identity, payment-instrument identity). Every derived proxy
  in this project carries an explicit confidence signal — it is never
  presented as ground truth.
- **SYNTHETIC** — has no real-data basis whatsoever; generated by
  `src/generator/` from a seed, deterministic per the requirements in
  `docs/SYNTHETIC_DATA_GENERATION.md`.

This is the same three-way split `docs/DATASET_AUDIT.md` and
`docs/GRAPH_FEASIBILITY.md` already use — this document is the canonical
per-entity reference the other docs point back to.

## 3. Phase 1C — customer-proxy candidate investigation

**Constraint carried in from the audit:** raw `card1`–`card6` tuple
equality is rejected — it produces a 14,112-row cluster with fraud rate
statistically indistinguishable from baseline (3.73% vs. 3.50%), i.e. a
false mega-cluster, not a customer (`docs/DATASET_AUDIT.md` §8). This
section investigates alternatives with the same discipline: measure, then
decide — do not pick whatever produces the prettiest graph.

**Method:** `scripts/investigate_customer_proxy.py`, run against the full
`train_transaction.csv` (+ `train_identity.csv` for the identity-linked
candidate). Full JSON output in `scratch_customer_proxy_output.json`
(regenerable, git-ignored).

### Candidates tested

| # | Candidate | Fields | Unique clusters | Singleton rate | Mega-cluster (≥500) row share | Largest cluster | Top-cluster fraud rate vs. base (3.499%) |
|---|---|---|---|---|---|---|---|
| A | `card1-6` (baseline, already rejected) | 6 | 14,893 | 27.55% | **57.62%** | 14,112 | 3.73% — indistinguishable from base |
| B | `card1-6` + `addr1` + `addr2` | 8 | 43,071 | 40.42% | 28.24% | 9,900 | 4.37% |
| C | `card1-6` + `P_emaildomain` | 7 | 45,960 | 41.71% | 29.78% | 5,590 | 3.27% |
| **D** | **`card1-6` + `addr1` + `P_emaildomain`** | **8** | **94,873** | **49.13%** | **10.41%** | **4,002** | **1.97%** |
| E | `card1` + `card2` + `addr1` + `P_emaildomain` | 4 | 92,690 | 48.99% | 10.61% | 4,002 | 1.97% |
| F | `card1-6` + 24h time window | 7 (6+bucket) | 195,326 | 60.03% | **0.196%** | 648 | 0.00% |
| G | `card1-6` + `DeviceInfo` (identity-linked subset only, n=144,233) | 7 | 29,014 | 57.30% | 15.70% | 2,736 | 5.45% (subset base rate 7.847%) |

### Finer analysis of the chosen candidate (D)

Cluster-size percentiles: median 2, 75th pct 4, 90th pct 10, 95th pct 20,
99th pct 72, max 4,002. Fraud rate by cluster-size band (measured, not
assumed):

| Cluster size band | Rows | Fraud rate |
|---|---|---|
| 1 (singleton) | 46,609 | 2.611% |
| 2–9 | 139,778 | 2.877% |
| 10–49 | 171,640 | 2.991% |
| 50–499 | 171,010 | 4.252% |
| 500+ | 61,503 | 4.907% |

There is a real, monotonic — but weak — upward trend (2.61% → 4.91%,
about 1.9x from smallest to largest band), **not** the kind of sharp
separation that would make "large cluster" a strong fraud signal on its
own. This is worth stating precisely rather than rounding to either
"clusters mean nothing" or "clusters are rings": the honest read is that
larger clusters skew mildly higher-risk (plausibly correlated with
certain BIN ranges / regions / merchant categories more than with
coordination), which is exactly why they must not be treated as
customer identities.

### Findings, per candidate

- **A (raw card1-6):** confirmed unsafe, as already established.
- **B, C:** narrowing by only one additional field each barely helps —
  mega-cluster row share stays above 28%. Not defensible.
- **D, E:** best balance among the "persistent identity" candidates —
  mega-cluster row share drops to ~10.4–10.6%, singleton rate rises to
  ~49% (a large, honest "we can't link this to anything" bucket, which
  is itself more truthful than forcing every row into a group). D and E
  are statistically near-identical; D is chosen because it uses the full
  `card1`-`card6` set at no extra cost and is marginally tighter on
  mega-cluster containment.
- **F (time-windowed):** the only candidate that essentially eliminates
  mega-clusters (0.2% row share) — but it does this by changing what's
  being measured. Multi-member cluster temporal span averages **0.48
  days** (~11.5 hours) — this is a same-day **transaction session**
  grouping, not a persistent customer relationship. It is a legitimate,
  useful signal in its own right (a tight, real "these transactions
  plausibly happened in one sitting" grouping) but is **not** a
  substitute for `customer_proxy` and is not implemented in this phase —
  flagged as a candidate future signal (`shared_session_context`), not
  built now, to avoid scope creep beyond what Phase 1 asked for.
- **G (identity-linked, + DeviceInfo):** still 15.7% mega-cluster row
  share on the already-small, already-biased 24%-coverage subset —
  confirms (again) that `DeviceInfo` doesn't meaningfully sharpen
  customer resolution, consistent with `docs/DATASET_AUDIT.md` §9.

### Decision

**`customer_proxy` = candidate D** (`card1|card2|card3|card4|card5|card6|addr1|P_emaildomain`),
implemented in `src/generator/customer_proxy.py`, with an explicit,
mandatory **confidence tier** carried alongside every ID:

| Tier | Cluster size | Meaning | Usable as a graph entity? |
|---|---|---|---|
| `singleton` | 1 | No repeat signal at all — honest "unknown" | Yes, trivially (represents itself only) |
| `small` | 2–49 | Plausible individual/household repeat use | Yes |
| `large_low_confidence` | 50–499 | Usable but flagged — could be a legitimate high-frequency account, could be attribute coincidence | Yes, but downstream ring/graph logic must treat this tier cautiously (matches the design doc's own multi-signal-required principle for shared IPs, Section 4 Q8) |
| `mega_unresolved` | ≥500 | Not treated as one entity at all — **individualized**: each transaction gets its own unique proxy ID instead of being merged | No — deliberately excluded from customer-level ring-forming logic |

**This decision does not claim `customer_proxy` is a validated customer
identity.** It claims: this is the least misleading of seven measured
strategies, it is transparent about its own uncertainty via the
confidence tier, and it refuses to silently merge the ~10.4% of
transactions whose shared attributes are best explained by coincidence,
not identity. `payment_instrument_proxy` uses the same tiering machinery
but a narrower field set (`card1`–`card6` only) and is **far coarser**
(57.6% mega-cluster row share) — it is documented and available, but any
future ring/graph logic must weight it much less heavily than
`customer_proxy`, and must never treat it alone as sufficient evidence of
shared identity.

**No entity in this project should ever present `customer_proxy_id` or
`payment_instrument_proxy_id` as a real, verified identity** — every
downstream use (graph edges, ring generator, feature engineering) must
carry the confidence tier alongside the ID.
